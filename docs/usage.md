# 使い方ガイド

xangi-searchの導入、検索、FACT管理、設定方法を説明します。

## xangi extensionとして使う

リポジトリのルートで次のコマンドを実行します。

```bash
uv sync --extra vector
xangi extension link ./xangi-extension.json
xangi extension start xangi-search
xangi extension doctor xangi-search
```

processは先に起動し、埋め込みmodelとindexをバックグラウンドで読み込みます。
`xangi extension start`の成功はHTTPの起動完了を表し、検索準備の完了は
`xangi extension doctor xangi-search`または`GET /health`の`ready: true`で確認します。
準備ができたら、xangiのExtensions画面で`xangi-search`の`Open`を押します。詳しい導入手順は
[セットアップガイド](../XANGI_SETUP.md)を参照してください。

## Web UI

### 検索

`検索`タブへキーワードや探したい内容を入力すると、関連するファイルが表示されます。
検索方式は通常`Hybrid`がおすすめです。

- `Hybrid`: 意味検索とキーワード検索を組み合わせる
- `Vector`: 意味の近さで検索する
- `Keyword`: 文字列の一致を中心に検索する

### FACT

`FACT`タブでは、長く覚えておきたい事実を追加・編集・無効化できます。FACTは通常の
ファイル検索にも利用されます。長いログや文書全体ではなく、1件につき1つの事実へ絞ります。
APIでは`GET /facts/{id}`で1件だけ取得でき、無効化済みFACTも`is_active: 0`として確認できます。

### 設定

`設定`では次の項目をワークスペースごとに変更できます。

- 検索方式、表示件数、最低関連度
- 自動index更新のON/OFFと間隔
- ディレクトリごとの検索重み
- 時間減衰
- FACTのMarkdown書き出し先

設定とindexはワークスペースの`.xangi-search/`に保存されます。起動時と標準30分間隔で、
変更されたファイルだけを再indexします。

## AIエージェントから使う

同梱の[`xs-xangi-search`スキル](../skills/xs-xangi-search/SKILL.md)をワークスペースへ追加すると、
AIエージェントが検索とFACT管理を使うための手順を共有できます。追加先や`AGENTS.md`の変更は、
初回setup時とextension更新後に同梱版とworkspace側を比較し、実質的な差分がある場合だけ提案します。
ユーザーが選択するまでworkspaceは変更しません。

## 単独CLIとして使う

xangiを介さず、コマンドラインからも利用できます。

```bash
# indexを作成
uv run xangi-search --workspace /path/to/workspace index

# 検索
uv run xangi-search --workspace /path/to/workspace search "検索語"

# Web UIを起動（既定: http://127.0.0.1:7891/ui）
uv run xangi-search --workspace /path/to/workspace serve
```

vector依存を使わない軽量構成では、セットアップを`uv sync`にして各コマンドへ
`--no-vector`を付けます。Hybridはkeyword検索へ切り替わります。明示的な`--mode vector`は利用不能エラーになります。`search --limit`と`evaluate --k`は正の整数のみ受け付けます。

## トラブルシューティング

### 初回indexが終わらない

`xangi extension doctor xangi-search`を実行し、`initialization_phase`と
`initialization_error`を確認します。低速なCPU、cold cache、大きなindexでは初期化に30秒以上
かかってもprocessは停止されません。準備中の検索requestはHTTP 503と`Retry-After: 2`を返します。
`start`の成功はindex完了を意味しません。

既存indexがある場合は起動時更新中も`ready: true`で検索できます。更新に失敗した場合も既存indexを
使い続け、`degraded: true`と`last_reindex_error`で失敗内容を確認できます。

### 意味検索が使えない

`uv sync --extra vector`を実行してからextensionを再起動します。vector依存がない場合は
自動的にkeyword検索へ切り替わります。

### 検索結果が少ない

検索語を短くする、`Keyword`へ切り替える、最低関連度を下げる、対象ディレクトリの重みを
確認する、の順に試します。

### 設定を初期化したい

設定とindexは`.xangi-search/`にあります。削除すると再作成されますが、indexの再構築が必要です。
必要なFACTや設定を確認してから操作してください。

### 検索対象からパスを除外する

設定ファイルが存在しない場合だけ既定値を使います。JSONの破損、読み取りエラー、設定値の不正がある場合は、ファイル名と原因をエラー表示し、起動・CLI索引作成を中止します。追加の除外設定を空にして処理を続けることはありません。設定ファイルを修正してから再実行してください。APIからの不正な設定更新は拒否し、現在の設定と保存済みファイルを保持します。

`PUT /settings`の`exclude_paths`で、ワークスペース相対のファイル・ディレクトリを指定できます。
既定は空配列で、既存の除外規則は引き続き有効です。glob、絶対パス、`..`は使えません。
ディレクトリを指定するとその配下を除外しますが、同じ名前で始まる別ディレクトリには影響しません。

```json
{"exclude_paths": ["output", ".cache", "logs/monitor-activity", "logs/tool-trajectory"]}
```

保存時と起動時に、除外対象の本文・FTS・ベクトルを索引から削除します。
自動indexが無効でも適用されます。元ファイルとFACTは削除しません。
SQLiteファイルの物理サイズは自動では縮小しません。
除外解除後は「今すぐ更新」または`POST /reindex`で再登録します。
設定は`.xangi-search/settings.json`に保存され、CLIのindex処理にも適用されます。
設定画面（1行1パス）またはAPIから編集できます。

環境ファイル（`.env`、`.env.*`、`*.env`、大小文字・階層不問）は索引と両grep経路で常に除外します。設定画面の「検索から除外するパス」に相対パスを1行1件入力できます。起動時・設定保存時に既存本文・FTS・ベクトルも削除し、自動indexが無効でも適用します。元ファイルとFACTは保持し、除外解除後は「今すぐ更新」で再登録できます。重み0は候補選定後の調整なので、ログの候補占有を防ぐには除外設定を使います。DBの論理削除は、未使用ページ・バックアップ・過去ログからの完全消去を保証しません。

## xangiホームへの移動

xangi経由で開いた画面の左上に、家アイコン付きの「xangiホーム」ボタンを表示します。Studioと同じ44pxの枠付きボタンで、同じ環境のトップへ移動します。検索・設定操作とは別の共通ナビゲーションとして配置しています。単独起動時は表示しません。

### 起動順の設定

初期化グループ対応xangiでは、既定でgpuグループの他拡張と初期化を直列化する。CPU運用などで不要ならホストのextensions.jsonの対象レコードに `"startup": null` を指定する。複数GPUではexclusiveGroupを分け、モデルの実際のデバイス設定も別途合わせる。ホスト未対応の場合は従来の起動動作となる。

### 読み取り専用で使う

サーバーを起動する環境に `XANGI_SEARCH_READ_ONLY=true` を設定すると、設定変更、FACTの追加・編集・削除、
手動の索引更新をHTTP 403で拒否します。既定は無効です。`GET` と `POST /agent`、起動時・定期的な
差分索引更新は継続します。UIでは設定とFACTを閲覧でき、変更操作は無効になります。
`GET /settings` と `GET /health` の `read_only` で状態を確認できます。APIから解除できません。
変更には起動環境の変更とプロセスの再起動が必要です。この設定はHTTP APIの変更制限であり、
ファイル権限やローカルCLIの書き込み権限を制限するものではありません。

### FACT出力先の移行

出力先は `.xangi-search/` 内のMarkdownに限定され、既定は `.xangi-search/facts.md` です。
生成ファイル以外の既存ファイルやシンボリックリンクは上書きしません。
旧設定がこのディレクトリ外を指す場合、起動時に新しい既定の出力先を使い、他の検索設定は維持します。
設定ファイルへの保存は次の設定更新時、Markdownの書き出しは次のFACT変更時に行います。
SQLiteに保存済みのFACTを引き継ぎ、DBが空なら設定された出力先を優先して取り込みます。旧設定の移行時は旧設定の出力先を優先します。現在のsnapshotが存在して空なら、古いFACTを復活させません。新しいsnapshotは本文をJSON recordとして保持する形式2で、旧形式も読込み可能です。形式2からの復元には対応版を使ってください。
旧ファイルは変更・削除しません。バックアップ対象に `.xangi-search/facts.md` とSQLiteを含めてください。

## 検索品質の確認

時間減衰ONは更新直後1倍、15日以上経過で下限0.5倍です。数値不明の一律半減や検索取得回数の加点はありません。mtimeを取得できない場合は1倍です。検索語には `30,958` / `30958`、`00:48:48` のような単独の値も使えます。

改善時は最新情報・過去の決定・書籍・数値の正解資料と検索語を先に固定し、候補取得から最終順位まで実APIで比較してください。固定候補内の並べ替えは補助評価です。正解が候補にない場合は索引内容や項目名の省略も確認します。数値をまとめる資料は項目名・単位・確認日を残します。評価の生JSONは検索対象外へ保存し、検索コピーを元資料として再評価しないようにします。

## 更新日時による忘却と既存利用者への影響

### 設定の保存先と既定値

忘却の既定値は変更せず `false`（OFF）です。`src/xangi_search/settings.py` の `SearchSettings.forgetting` と設定読込時の省略値で定義しています。workspaceごとの保存先は `<workspace>/.xangi-search/settings.json` で、UIの設定画面または `PUT /settings` から変更できます。`GET /settings` で確認でき、検索ごとの `forgetting` 指定はその検索だけ保存値を上書きします。更新時に既存のON/OFFやパス別重みをリセットしません。パス別重みの初期値は1.0で、knowledgeの1.5倍などは個別workspaceの設定です。

### ONでの計算方法

係数は `max(0.5, min(1.0, 1 - 経過日数 / 30))` です。更新直後1倍、15日以上で0.5倍となります。`src/xangi_search/index.py` の `FRESHNESS_DECAY_DAYS=30` と `FRESHNESS_FLOOR=0.5` で定義し、今回この2値をUI/API設定には追加していません。mtimeが取れない場合と未来のmtimeは1倍です。ファイル名の日付や検索取得回数・最終取得日による減衰・補強をやめるため、既存のON利用者は順位が変わります。古い資料が正解の質問では悪化する場合があります。

OFF利用者には日時による順位補正はありません。ただし、後述する数値・識別子の検索修正はOFFでも適用されます。既存の参照履歴カラムは互換性のため保持し、文書検索では更新しません。ON時の応答は `decay=1.0`、`freshness` が減衰係数です。FACTの順位計算は変更しません。

### 回答に採用した資料の日時更新

配布スキルは、原文確認後に回答の根拠として採用した資料へ `touch -c -m` を実行し、statで反映確認する運用です。本文とatimeは変えず、mtimeを「内容更新または回答への採用」の日時として扱います。検索候補に出ただけの資料や検索コピー、コード・設定・実行時データ・シンボリックリンクは対象外です。

これはエージェントが判断して実行する手順で、自動フックではありません。サービス更新だけでは既存利用者のスキルへこの手順は追加されず、配布スキルの更新が必要です。日時変更権限が必要で、失敗時は未反映として報告します。mtimeだけの変更はGitで同期されません。mtimeは検索時に読むので再indexは不要ですが、上位になる保証はありません。

コピーでmtimeが新しくなる場合もあるため、本文中の情報が新しいことの保証には使えません。比較実験では採用を理由に日時を書き換えず、評価条件を固定してください。

### 数字・識別子の検索

数字だけの検索は桁区切りの有無を正規化し、`30,958` と `30958` を同じ数値として検索します。長いIDの一部分は一致としません。時刻（例 `00:48:48`）と英数字の識別子（例 `v0.2.3`、`62a12595`）も分割しません。keyword/hybridでは単独の数値・識別子に一致する候補に絞り、通常の文章検索と明示的なvector検索は従来の挙動を維持します。日本語などを含む複合検索語の数字正規化は今回の対象外です。

句読点やラベル区切りに接する値も一致させ、小数・長いID・より長い時刻の一部は除外します。完全一致の判定は候補件数の打切り前に行います。補助grepは文字列一致で検索し、UI・検索agent・Preflightにも反映します。

## 任意の事前検索（Preflight）

通常はextensionとスキルで必要な時に検索します。Preflightは、各turnでLLMへの入力前に検索し、根拠候補を追加する任意のhookです。推奨・必須ではなく、希望する場合だけworkspaceの `hooks/hooks.json` に設定します。毎turnの検索待ち時間・追加contextが増え、短い相づちなどでは有用な候補が得られないこともあります。既存hookは更新時に自動で有効化・無効化しません。導入手順は [セットアップのオプション](../XANGI_SETUP.md#オプション-回答前の事前検索preflight) を参照してください。

Preflightは本文の12,000文字制限に加え、JSON escapeと外側の説明・改行を含む出力全体を14,000文字以内に収めます。
